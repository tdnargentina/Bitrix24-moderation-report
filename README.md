# 📊 Отчёт по модерации приложений Bitrix24

**Задача:** сформировать отчёт по модерации приложений за сентябрь 2026 года и добавить топ-3 причин возврата для каждого модератора.
**Технологии:** PHP, JSON, CSV, GitHub, Render.
**Демо:** https://bitrix24-moderation-report.onrender.com/index.php

---

## 1. 🧩 Принятые решения

В требованиях и исходных данных были моменты, которые допускали разные трактовки. Я выбрал следующие правила:

- **Период отчёта:** сентябрь 2026 года по московскому времени. Заявка учитывается среди закрытых, если её статус — `approved` или `returned`, а дата `CLOSED` попадает в сентябрь.
- **Типичное время обработки:** медиана длительности закрытых заявок. Некорректные и отрицательные значения длительности исключаются из расчёта.
- **Заявки в работе:** считаются по всем переданным данным со статусом `in_progress`, независимо от даты создания.
- **Неизвестный модератор:** если модератор есть в заявках, но отсутствует в справочнике пользователей, он всё равно попадает в отчёт.
- **Топ-3 причин возврата:** причины группируются отдельно для каждого модератора по количеству возвратов за отчётный период.
- **Объединение формулировок:** варианты «нет иконки», «нет иконки приложения» и «отсутствует иконка приложения» объединены в категорию **«Нет иконки приложения»**. Другие похожие формулировки пока не объединяются автоматически.

## 2. 🔎 Неожиданности в исходных данных

### Дубликат заявки `4104`

Одна и та же заявка встретилась в исходных JSON-файлах дважды. Это обнаружилось при проверке количества записей и повторяющихся ID.

**Решение:** программа удаляет дубликаты по ID и учитывает заявку только один раз.

### Неизвестный модератор `ID 19`

В заявках обнаружился модератор, которого нет в `users.json`.

**Решение:** не исключать его заявки, а добавить в отчёт с обозначением `Неизвестный (ID 19)`.

### Некорректная длительность заявки `4109`

Заявка создана в `12:00`, а закрыта в `09:00` того же дня. При таком порядке дат длительность получается отрицательной.

**Решение:** заявка учитывается в количестве закрытых за сентябрь, но исключается из расчёта медианы времени обработки.

### Разные формулировки одной причины возврата

Причины вроде «нет иконки» и «отсутствует иконка приложения» описывают одну проблему, но изначально считались раздельно.

**Решение:** объединил известные варианты в одну категорию и пересчитал отчёт.

## 3. 🤖 Работа с ИИ-агентом

Я использовал ИИ-агента для разработки приложения, но не принимал его результат без проверки.

В процессе работы я:

- проверял расчёты на исходных данных;
- уточнял правила обработки нестандартных случаев;
- заметил, что похожие причины возврата учитывались отдельно;
- попросил объединить формулировки, после чего проверил обновлённый результат.

**Вывод:** ИИ ускорил разработку, но для получения корректного результата потребовались уточнение требований, проверка исходных данных и независимая валидация расчётов.

## 5. 🚀 Что можно улучшить дальше

Если бы на задачу был ещё один день, я бы сосредоточился на следующих направлениях:

1. **Автоматические тесты** — для дубликатов, неизвестных модераторов, граничных дат, некорректных длительностей и группировки причин.
2. **Нормализация причин возврата** — справочник синонимов, чтобы объединять похожие формулировки по согласованным правилам.
3. **Визуализация** — графики по модераторам и причинам возврата, более удобный интерфейс и favicon.
4. **Безопасность** — проверка загружаемых JSON-файлов, обработка ошибок и настройка доступа. Перед использованием с реальными данными нужно отдельно оценить безопасность публичного размещения на GitHub и Render.
5. **Журналирование** — запись предупреждений о дубликатах, неизвестных пользователях и некорректных данных для упрощения диагностики.
